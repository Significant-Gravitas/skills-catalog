# How skills run on the AutoGPT Platform (read before judging "platform fit")

- An **expert** is a hired AI teammate (persona in `experts/<key>.yml`: identity, voice, boundaries, day_one, routines) that bundles an ordered kit of skills (cap 150). Users hire several experts into a team led by AutoPilot ("Otto"); experts can consult, delegate to and hand off to teammates.
- **Skill loading**: the model sees only each skill's `name` + `description` (+ optional `triggers`) in an `<available_skills>` block. It calls `read_skill` to load the SKILL.md body and the list of sibling files, and `read_workspace_file` to open `references/`, `templates/`, `scripts/`, `examples/`. So the description decides whether the skill ever triggers, and the body must route to supporting files by relative path. Frontmatter fields other than name/description/triggers are dropped (`argument-hint`, `user-invocable`, `allowed-tools` are ignored).
- **Tools a skill can rely on**: `bash_exec` (E2B Linux sandbox; Python/Node; can run bundled scripts; no user secrets), `web_search`, `web_fetch`, `browser_navigate`/`browser_act`/`browser_screenshot`, `run_block` (AutoGPT blocks: Google Gmail/Sheets/Docs/Drive/Calendar/Slides, Slack, HubSpot, Notion, Linear, GitHub, Airtable, Apollo, Exa, Firecrawl, Perplexity, Tavily, DataForSEO, Stripe, Todoist, Twitter/X, Reddit, Discord, Telegram, WordPress, Medium, Smartlead, ZeroBounce, Jina, Enrichlayer, generic HTTP, etc.), `run_mcp_tool` (MCP servers the user connected), `connect_integration` (ask the user to connect an account), `ask_question` (structured question to the user), `memory_store`/`memory_search` (durable memory), `read_workspace_file`/`write_workspace_file` (user's workspace files), `schedule_routine`/`schedule_followup` (recurring work), `todo_write`, `consult_teammate`/`delegate_to_expert`/`handoff_to_expert`. Outward actions (sending email, posting, writing to CRM/accounting) go through the platform's approval flow; a good skill drafts first and asks for approval before any external side effect.
- **Poor fit signals**: Claude-Code-only constructs (slash commands, `$ARGUMENTS`, `CLAUDE.md`, hooks, `~/.claude` paths, Task/subagent tool, plugin-namespaced commands), links or paths to files not shipped inside the package, dependence on a named SaaS with no block/MCP and no graceful fallback, instructions to install heavy toolchains, assuming persistent local state that the platform does not keep, sponsor/vendor tables, or stale model/tool names.
- **Good fit signals**: asks for the minimum inputs up front, degrades gracefully when an integration is missing (ask for a CSV/export/paste), uses the sandbox for arithmetic and file handling, labels every number as sourced or assumed, logs approvals, hands off to the right teammate at a clear boundary, and produces a named artefact the user can reuse.
